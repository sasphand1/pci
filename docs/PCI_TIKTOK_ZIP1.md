# PCI TikTok ZIP 1 — private ingestion and administrative validation

Base: `d4a468865ddcffebe24c641c17289e76030e225d`. Module 1 and Module 3 only; Module 2 and all existing ranking contracts are unchanged. Do not enable public TikTok rankings with this release.

## Operating contract

- Use a permitted Scrappa account and verify source terms, data provenance, and publication rights. Scrappa is a third-party source, not the official TikTok API. The existing profile/posts response contract and continuation fields must be checked against live responses before enabling unattended operation. No credentials are bundled.
- People → TikTok: save and activate a key as Owner, check and stage a public account, then collect to Hub. Check and stage each consume a request. Collection costs 2–4 requests (one profile plus up to three pages), charged locally before each outbound request, including failures. The local counter assumes one Scrappa credit per request; check actual provider billing. No automatic retry or invented continuation cursor. A changed staged identity, foreign post author, failed request or invalid schema prevents snapshot publication.
- Full recent-video averages require ten distinct eligible videos with the relevant metric available for every video. Pinned, sponsored and invalid entries are excluded. Bounded pages are a sample, not an exhaustive video history, a 30-day upload count, or lifetime views. Missing data is null, never zero or a stale average. The provider's ordering and pagination still need live verification.
- An Owner can link the candidate to the exact slug of an existing People record (visible in People), unlink it, inspect collection history, or remove the staged candidate and its private observations. The identity link is explicit and one-to-one; no name-based guessing. Editors can inspect candidates and history; only Owners can collect, link, remove, change keys or enable the schedule. Removing a candidate does not remove an existing live person. TikTok-only candidates stay staged for ZIP 2.
- PostgreSQL migration `130_scrappa_refresh.sql` adds the link, refresh state and coherent snapshots. The same additive DDL is bootstrapped after the registry and Hub schema on Hostinger, under the normal advisory lock. Existing candidate observations are retained but are not retroactively fabricated into coherent snapshots. A successful refresh atomically replaces the candidate's latest projection and keeps historic observations; incomplete cohorts are labeled partial. Candidate snapshots/observations/latest readings expire after 90 days through the existing retention task. Profile avatar URLs and bios are not included in new historical snapshots.
- Data Hub displays private staging coverage, 15-day freshness, full samples, quota and an Owner-only scheduler switch. `GET /api/v1/admin/bucket/scrappa/status` and `GET /api/v1/admin/bucket/scrappa/candidates/:id/snapshots` are authenticated read endpoints. History is bounded to the most recent 20 snapshots. Existing Hub account/ranking interfaces are unaffected.

## Scheduled refresh (off by default)

1. Confirm source terms, quota and live response compatibility. Manually collect five verified public creators and compare counts with the source; verify the Hub and history show expected values, nulls and partial status.
2. Set `PCI_SCRAPPA_AUTO_REFRESH=true` in Module 1's API and worker environments (one scheduler owner, existing embedded or standalone worker). Redeploy Module 1. No new service is needed. Then explicitly enable scheduled TikTok refresh in Owner → Data Hub. If the worker flag is absent or source switch is disabled, no scheduled API requests occur. The switch controls scheduled collection; owner-confirmed manual collection remains available.
3. The scheduler attempts at most one candidate per hourly tick, oldest successful collection first, due after 15 days and with a 24-hour per-candidate attempt cooldown. It stops scheduling when fewer than four credits remain below the 400-request scheduled ceiling, leaving a 100-request margin below the existing shared 500-request UTC-month hard cap. Concurrent manual requests share the same hard cap; a collection may fail safely if credit is consumed concurrently. No guaranteed refresh SLA: with 100 candidates, two-credit collections can use 400 requests for two passes; four-credit collections can use 400 for one pass. Actual eligibility and retries may reduce coverage. Automatic collection pauses 24 hours after authorization/rate-limit errors and six hours after three consecutive failures. One shared PostgreSQL run lease prevents overlapping collections and rejects expired writers.
4. To stop scheduled collection, disable the owner switch or remove the environment opt-in. In-flight collection may finish; no subsequent scheduled run should start. Keep the source private until ZIP 2 and permission validation.

## Validation and deployment

- The package helper enforces exact baseline and clean working tree, verifies payload hashes, applies only the declared files, uses lockfiles to install and runs `npm run check` in each of the three modules. It then uses disposable PostgreSQL 16 and Redis 7 containers bound to random localhost ports, migrates the empty `pci_test` database, and runs the repository integration suite plus the new Scrappa integration tests. Docker Desktop must be running. It never uses the production database. All checks must pass before Git staging, commit or push. Failed gates leave changes local for inspection, not deployed. No force push or broad staging.
- Changes to Module 1 and Module 3 deploy-trigger files follow the repository's existing convention. A successful normal push can trigger Hostinger deployment if Git auto-deploy is configured there. The repo does not expose Hostinger's deployment configuration; the helper cannot verify that remote deployment completed. Check the Hostinger status and API readiness, then run the five-creator manual validation above. Public website code is unchanged.
- Sandbox validation: dependency-free JS/TS suites, strict collector type check and changed TypeScript syntax transpilation. Full package install/build and live PostgreSQL tests are not verified in the sandbox: npm registry DNS is unavailable and PostgreSQL/Docker are not installed. The new database tests are in local test:db and GitHub CI. The deployment helper is supplied for Windows PowerShell and has not been executed in the Linux sandbox.

## ZIP 2 boundary

Promote verified candidates into the live unified creator registry with an explicitly reviewed metric policy; add TikTok-specific rankings and public profiles, any permitted avatar publication, and public UI. Do not treat the sample averages as comparable lifetime channel totals. Source/publication rights and production data validation remain hard gates. TikTok Broadcast posting is outside these two analytics ZIPs.
